Predicting whether a beneficiary will actually use an approved dental care
allowance, so that an unused budget can be spotted before the year closes
rather than after.

**[Open the live dashboard](https://dental-care-prediction.streamlit.app/)**

![Model evaluation](figures/model_evaluation.png)

## The problem

Health insurers approve dental care budgets that are then only partly consumed.
Money sits allocated against benefits nobody claims, and it cannot be moved
where it would be used. Predicting utilization at the point of approval turns
that into a planning decision instead of a year-end surprise.

## About the data

The framing comes from a year I spent on health insurance data pipelines at
CPAM Haute-Garonne. **The data here does not.** No CPAM record was used, and
none could be. `src/data_pipeline.py` generates 50,000 synthetic claims from a
known logistic process with a fixed seed, so anyone cloning this repository
reproduces the exact dataset, the exact model and the exact numbers below.

That has a consequence worth stating up front: because the target is drawn from
a linear process, this dataset is friendlier to a linear model than real claims
data would be. The benchmark below should be read as a demonstration of method,
not as evidence about which algorithm wins on actual health insurance data.

## Results

Three classifiers, 40,000 training rows, 10,000 held out. Metrics are computed
on the held-out split; the CV column is the mean 5-fold AUC-ROC on the training
split only.

| Model | AUC-ROC | CV AUC-ROC | F1 | Precision | Recall | Accuracy |
|-------|---------|------------|-----|-----------|--------|----------|
| **Logistic Regression** | **0.713** | 0.701 | 0.698 | 0.750 | 0.653 | 0.651 |
| Random Forest | 0.706 | 0.695 | 0.706 | 0.744 | 0.672 | 0.655 |
| XGBoost | 0.705 | 0.691 | 0.759 | 0.698 | **0.831** | 0.674 |

Numbers come straight from `models/results.json`, regenerated by
`python src/train.py`.

**Reading the table.** The interesting result is that the simplest model wins
on AUC, and the exploratory notebook explains why: plotted against each
predictor, the log-odds of utilization are close to a straight line, which is
the regime a logistic regression is built for. The gradient boosting model has
nothing extra to exploit and pays for its flexibility.

Three further points a single AUC hides:

- **The ranking is tight.** 0.713 against 0.705 is roughly one standard
  deviation of the cross-validation spread. These models are not meaningfully
  different, and claiming a winner would overstate the evidence.
- **0.71 is a ceiling, not an underfit.** No single feature separates the two
  classes strongly (the largest Cohen's d is 0.34, for age). The signal is
  thin and spread across many weak predictors.
- **The metric should follow the decision.** XGBoost recovers 83% of the
  beneficiaries who go on to use their benefit, against 65% for the linear
  model. If the cost of missing a user outweighs the cost of a false alarm,
  XGBoost is the better choice despite its lower AUC. The table reports both so
  the trade-off stays visible.

## How it is built

The parts worth looking at are less about the models than about keeping the
pipeline honest.

**One feature path, shared by training and serving.** `src/features.py` owns
every transformation, and `app.py` imports it rather than reimplementing it.
An earlier version of this repository did reimplement it, and drifted: the
dashboard flagged `high_claim` above 800 EUR while training used the 75th
percentile of the training split, 1511 EUR. Every prediction served was based
on a feature the model had never been trained on. `tests/test_features.py` now
asserts that scoring one row alone gives the same features as scoring it inside
the full frame.

**Data-dependent constants fitted on the training split only.** The
`high_claim` cut-off is a quantile, so computing it before the split would leak
test information into training. `build_training_sets` splits first, fits the
threshold on the training rows, and persists it to
`models/feature_config.json` so inference replays the same value instead of
recomputing or hard-coding it. The label encoders are fitted the same way, and
map an unseen category to -1 rather than raising.

**Scaling where it matters.** Claim amounts reach 2000 while utilization rates
sit in [0, 1]. Without standardisation, lbfgs hits its iteration cap without
converging, so the linear model runs inside a `StandardScaler` pipeline. That
also makes its coefficients comparable to one another, which is what the third
panel of the figure plots.

**Importances that work for every model family.** `feature_importances` unwraps
a pipeline, uses `feature_importances_` for tree ensembles and coefficients for
linear models. Before that branch existed the panel rendered blank whenever the
logistic regression won, which it does here.

## Quick start

```bash
git clone https://github.com/Mo199711/dental-care-prediction.git
cd dental-care-prediction
pip install -r requirements-dev.txt

python src/data_pipeline.py    # regenerate the seeded dataset
python src/train.py            # benchmark, artifacts and figure
pytest                         # 14 tests
streamlit run app.py           # dashboard on localhost:8501
```

The committed artifacts already match the committed data, so `streamlit run
app.py` works on a fresh clone without retraining.

## Limitations

- **Synthetic data.** The target is drawn from a logistic process, which is why
  a linear model performs as well as it does. Nothing here should be read as a
  finding about real dental claims.
- **No hyperparameter search.** The three models use reasonable defaults. Given
  how tightly they score, tuning would move the ranking around without
  changing the conclusion, so the README does not claim tuning it has not done.
- **No calibration.** Probabilities are used at a 0.5 threshold and have not
  been checked against observed frequencies. A budgeting use case would need a
  reliability curve and a threshold chosen from the cost of each error, not
  from the default.
- **No fairness audit.** `gender` and `income_bracket` feed the model. On real
  data, both would need a disparate-impact check before anything reached a
  decision process.
